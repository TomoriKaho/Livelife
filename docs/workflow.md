# GitHub 协作流程

团队用 Issue 讨论需求和分配工作，用 Project 查看进度，用 PR 评审改动，用 Milestone 组织阶段交付，最后通过 Release 发布版本。

从提出想法到交付版本，完整流程是：

**提出需求 → 成员讨论与表态 → 需求通过 → 拆分和分工 → 开发与测试 → PR 评审 → 合并与联调 → 阶段验收 → 发布版本。**

## 1. 随时提出需求

每位同学都可以随时提出项目需求，包括新功能、体验改进、技术方案和工程建设。

进入仓库的 **Issues → New issue**，选择合适的模板，写清楚：

- 用户遇到了什么问题，或团队需要解决什么问题。
- 希望实现什么效果。
- 本次建议包含哪些内容。
- 可以怎样验收，或还需要讨论哪些问题。

大型功能使用父任务模板，例如“实现兴趣订阅”；具体工作使用普通任务模板，例如“搭建共享测试服”。发现程序问题时使用 Bug 模板。

创建后，为 Issue 添加模块标签，并加入团队 Project。**未被通过的需求，在 Project 中设置为 `Backlog`。** 尚未确定交付阶段的需求可以先留在待讨论列表，讨论通过后再安排 Milestone。

### 讨论与通过

成员在 Issue 评论中发表意见。赞成时明确写“赞成”，也可以补充理由、建议或实现思路；需要调整时说明希望修改的内容。

**当半数以上成员发表赞成意见后，由需求负责人员将需求设置为 `Ready`** 需求负责人员在 Issue 中记录通过结果，方便大家回看。

尚未达到通过条件的需求继续放在 Backlog，成员可以继续讨论和完善。需求通过后，需求负责人员组织任务拆分，设置优先级、目标日期及负责人。

需求负责人员负责推进讨论、确认范围和安排交付；开发负责人（Assignee）负责具体任务的实施。

## 2. 用 Milestone 规划阶段交付

Milestone 表示一组需要在某个阶段完成的工作，例如“实现 MVP 版本”。进入仓库 **Issues → Milestones → New milestone**，填写名称、目标日期和交付目标。

假设 MVP 要交付兴趣订阅、地图和说明文档，可以这样安排：

```text
Milestone：实现 MVP 版本
├─ #10 实现兴趣订阅
│  ├─ #11 确定订阅数据结构与接口
│  ├─ #12 实现订阅后端接口
│  ├─ #13 实现兴趣设置页面
│  └─ #14 完成订阅联调与验收
├─ #20 实现地图功能
│  ├─ #21 确定地图方案与地点数据结构
│  ├─ #22 实现地点和活动查询接口
│  ├─ #23 实现地图页面与详情入口
│  └─ #24 完成地图联调与验收
├─ #30 完成使用与部署说明
├─ #40 初始化前端工程
├─ #41 初始化后端工程
├─ #42 配置自动检查
├─ #43 搭建共享测试服
└─ #45 完成 MVP 整体验收
```

每个计划在 MVP 中交付的任务，都在 Issue 右侧选择这个 Milestone。域名注册、部署配置、调研和文档等工作，也可以作为独立任务加入。

Milestone 描述写整体交付条件，例如：用户可以保存和修改兴趣、地图可以展示活动、前后端联调完成、使用与部署文档可用。

Milestone 的进度按关联条目的关闭情况展示。父任务和子任务都加入时，会议中结合实际验收结果判断进度。

## 3. 拆分任务，分配负责人

大功能的父 Issue 写整体目标、范围和整体验收条件。子 Issue 写具体工作、验收条件和依赖，分别设置 Assignee、Labels、Project 和 Milestone。

### 创建子 Issue

有两种操作方式：

**直接创建：**

1. 打开父 Issue。
2. 在正文下方点击 **Create sub-issue**。
3. 填写标题、描述及负责人等字段，点击 **Create**。
4. 需要连续创建时，选择 **Create more sub-issues**。

**关联已有任务：**

1. 通过 **New issue** 使用模板创建具体任务。
2. 打开父 Issue，点击 **Create sub-issue** 旁的菜单。
3. 选择 **Add existing issue**，搜索编号或标题并关联。

第二种方式便于统一使用任务表单。添加子任务需要至少 Triage 权限。

同一个人完成的小步骤可以写成 Issue 内的勾选清单；需要独立分工、讨论或验收的工作适合建立子 Issue。

依赖在正文中写明，如“依赖 #11 完成接口约定”，也可以使用 GitHub 的依赖关系功能。遇到阻塞时，在评论中说明卡点、所需帮助和关联任务，方便队友接续处理。

## 4. 用 Project 查看团队进度

团队长期使用一个 Project，通过不同视图查看需求、任务和成员分工。

### 状态与负责操作的人

| 状态        | 含义                                       | 谁来更新                         |
| ----------- | ------------------------------------------ | -------------------------------- |
| Backlog     | 需求待讨论、尚未通过                       | 提出需求的成员或需求负责人员     |
| Ready       | 需求已获得半数以上成员赞成，等待安排或开始 | 需求负责人员                     |
| In Progress | 任务正在实施                               | 开发负责人                       |
| In Review   | 工作已提交评审或正在验收                   | 验收负责人                       |
| Done        | 已达到验收条件                             | 父任务是否完成由需求负责人员确认 |

通过的需求拆成子任务后，需求负责人员将已明确范围的子任务设为 Ready，方便成员领取。需求讨论针对父需求进行，其范围内的实施子任务随拆分安排进入开发；新增加的需求另行讨论。

Ready 是排期和领取入口。开始具体任务前，负责人确认依赖和资料齐备，再设为 In Progress。

在 Project 表格中点击任务的 Status 单元格，选择对应状态；在看板中也可以将卡片拖到对应列。当前由成员手动维护，后续逐步加入自动更新。

### 优先级与日期

需求负责人员在 Project 中设置 Priority 和目标日期。未加入 Milestone 的任务可以先不标记优先级。优先级约定如下：

| 优先级 | 用途                             | 示例                         |
| ------ | -------------------------------- | ---------------------------- |
| P0     | 需要立即处理，影响团队开发或交付 | 主分支构建失败、测试服不可用 |
| P1     | 当前阶段优先完成                 | 订阅接口、地图基础展示       |
| P2     | 后续安排或可以延期               | 地图动画、额外体验优化       |

维护者在 Project 的表格视图最右侧添加字段：**New field → Single select**，名称为 Priority，添加 P0、P1、P2。目标日期使用 Date 字段。之后直接在任务行中选择值。

优先级统一保存在 Project 中；模块使用 Issue 标签，例如 frontend、backend、infra、docs。阶段归属使用 Milestone。

给父 Issue 添加 epic 标签。在视图顶部通过过滤条件选择 Milestone、Status、Assignees 或 Labels，再保存视图。“当前阶段”排除 epic，“功能概览”只显示 epic。

这些视图展示同一批工作项的不同部分。Project 主要以 Issue 追踪任务，关联的 PR 从 Issue 中进入。阶段结束后归档已完成任务，保持日常看板简洁。

## 5. 从任务到 PR

成员领取 Ready 中的任务，设置自己为 Assignee，创建功能分支，并将状态改为 In Progress。

分支、commit 和本地操作见 [贡献指南](../CONTRIBUTING.md)。提交和 PR 标题统一采用：

```text
feat: (订阅) 实现兴趣订阅接口
fix: (地图) 修复地图标记点击异常
docs: (部署) 补充部署说明
```

分支名使用 `feat/12-subscription-api` 等形式。

### 创建与填写 PR

1. 推送功能分支。
2. 在 GitHub 点击 **Compare & pull request**，或 **Pull requests → New pull request**。
3. base 选择 main，compare 选择自己的分支。
4. 填写模板中的关联 Issue、改动、验证结果及适用的兼容性说明。
5. 有预览环境时提供链接和版本，接口改动提供调用示例。前端 PR 无需提交界面截图或录屏。

可以提前开 Draft PR，展示进展和讨论方案。开发与自测完成后，点击 **Ready for review**，再从右侧 **Reviewers** 选择一名队友。此时将关联任务设为 In Review。

Ready for review 表示作者已经准备好接受正式评审。创建时已完成的工作，可以直接开普通 PR。

### 关联 Issue

在 PR 正文中引用任务编号。完整解决并满足验收条件时写：

```text
Closes #12
```

合并到默认分支后，GitHub 自动关闭对应 Issue。部分完成或仍需合并后验收时写：

```text
Refs #12
```

这会留下引用，方便在原 Issue 中继续跟进。

## 6. 测试、评审与修改

作者按 Issue 自测，评审者根据验收条件独立检查代码和功能。具体步骤见 [测试说明](testing.md)。

预览部署是计划建设的协作入口，配置后成员可以推送分支，再运行 Actions 获取链接。前端预览通常连接共享测试后端；接口同步变化时使用配套后端。部署配置和运行方法见 [部署说明](deployment.md)。

评审者可以拉取 PR 在本地运行，也可以打开预览链接或安装测试构建，并在 PR 中记录测试版本、步骤和结果。

| 评审结果        | 含义                 |
| --------------- | -------------------- |
| Comment         | 提问、建议或一般反馈 |
| Request changes | 指出需要修改的问题   |
| Approve         | 同意合并             |

作者修改后继续 commit 和 push，新提交自动进入原 PR。main 有相关更新时，在功能分支执行 `git fetch origin`、`git merge origin/main`，处理冲突并验证受影响功能。

## 7. 合并与完成任务

至少一名队友批准，必要检查通过，评审意见处理完成后，合并 PR。

默认使用 **Squash and merge**：把 PR 的多次提交合成 main 上的一次提交。例如页面实现、修复按钮和处理评审意见，可以整理为 `feat: (订阅) 实现兴趣订阅页面`。

希望保留每次提交的独立步骤时，可以选择 **Create a merge commit**，将完整提交历史合入 main。合并完成后删除远程功能分支，PR 保留讨论与提交记录。需要长期保存的中间版本可以打 Tag；撤销已合并改动通常使用 revert 提交。

共享测试部署配置完成后，main 更新触发部署，团队在共享环境完成联调。任务通过验收后关闭 Issue，并将 Project 状态设为 Done。父任务由需求负责人员确认整体验收后关闭。

遗留问题记录为 Bug Issue，标明影响、负责人及计划处理阶段。

## 8. 阶段验收与 Release

Milestone 组织计划交付的任务，Release 记录实际交付的版本。

以 MVP 为例，订阅、地图、说明文档及基础工程完成后，团队在共享测试服验收完整流程，记录通过验收的提交 SHA 和已知问题。

发布负责人按以下步骤交付：

1. 确认本次版本的功能、测试结果和文档。
2. 在验收过的提交上创建 Tag，例如 v0.1.0。
3. 构建该版本的安装包及服务端产物。
4. 进入 **Releases → Draft a new release**，选择对应 Tag。
5. 填写功能变化、安装或部署方法、兼容性及已知问题，附上需要的文件。
6. 按发布安排部署并验证正式环境，公开 Release。

Android APK 可以作为附件；iOS 通过已配置的测试或商店渠道分发，Release 中提供说明；网页与后端提供访问、部署及版本信息。GitHub 自动提供 Tag 对应的源码压缩包。

阶段目标完成后关闭 Milestone。发布工作可以单独用“发布 v0.1.0”Issue 跟进，记录构建、部署和版本说明的完成情况。

## 9. 团队自动化的建设顺序

目前先按上述步骤协作，自动化按以下顺序建设：

| 自动化             | 提供的帮助                       |
| ------------------ | -------------------------------- |
| PR 检查            | 自动运行格式、测试和构建         |
| Project 内置工作流 | 自动加入任务、同步已关闭任务状态 |
| 分支预览           | 提供合并前的前端与后端测试入口   |
| main 测试部署      | 更新共享测试环境                 |
| 版本发布           | 构建版本产物并执行发布部署       |
| 预览清理           | PR 关闭后清理对应资源            |

需求是否通过按成员表态决定，由需求负责人员更新 Ready。其他状态更新在自动化配置完成前由相关成员维护。
