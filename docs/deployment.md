# 环境、Actions 与发布教程

## 当前实施状态

frontend/ 已提供本地网页工程，运行 `npm run build` 后可用 `npm run preview` 查看构建产物；安装、端口及环境变量配置见 [工程规范](engineering.md#目录与启动命令)。backend/ 已提供本地 hello 服务，启动和检查步骤见工程规范；本分支尚无业务后端、Docker 配置、部署凭证、APP 构建配置或可执行工作流，没有已验证的远程服务地址。本地构建预览不代表正式工程已部署。

已确定后续采用 Docker Compose，首阶段仅本地网页演示和最小 Android 验证包，不要求共享测试服、分支预览或自动部署。以下服务器、Actions 和发布内容为后续实施教程；示例域名 example.com 必须替换。配置完成后，维护者补充真实地址、负责人、工作流、命令与恢复步骤。

## 分支与环境

| 代码来源            | 环境               | 更新规则                   |
| ------------------- | ------------------ | -------------------------- |
| 功能分支            | 本地或独立 preview | 推送后按需部署；后续可自动 |
| main 的已检查提交   | staging 共享测试服 | 合并后自动部署             |
| 已验收 Tag/固定产物 | production 正式服  | 明确发布版本时部署         |

main 是分支，不是服务器。测试服可跟随 main，正式服继续运行 v0.1.0，不必建立长期 develop 分支。课程初期可以一台机器运行多套独立容器，但服务、数据库、存储和凭证分开；资源不够时按需预览。

## Actions 的基本概念

工作流 YAML 放在 .github/workflows/。Event 决定触发时机；Workflow 包含 Jobs；Job 在 Runner 上执行若干 Steps。GitHub 可提供 Linux/macOS 等 Runner，也可配置自托管 Runner。Actions 执行检查和部署，服务器负责持续运行应用；定时采集、推荐和推送正式业务优先由后端任务系统负责。

建议逐步建立：

| 文件               | 触发                                   | 目的                            |
| ------------------ | -------------------------------------- | ------------------------------- |
| ci.yml             | pull_request；main push                | 格式、类型、测试与构建          |
| preview.yml        | workflow_dispatch；以后可限定分支 push | 分支预览                        |
| deploy-staging.yml | main push，同次检查通过后              | 共享测试服                      |
| release.yml        | 版本 Tag 或受控手动运行                | 固定版本构建、Release、正式部署 |

简单 Project 状态同步使用内置工作流。复杂 Issue/Project 联动需 GitHub API 和适当权限。Actions 不是已经配置好的项目测试，必须先实现真实脚本。

## 维护者搭建测试服教程

1. 创建“搭建测试环境”Issue，确定平台、预算、负责人和验收条件。
2. 购买或准备云服务器，创建部署用户，配置网络入口和受控访问。
3. 按选型安装容器运行环境，建立独立 staging 服务和数据库。
4. 注册域名，在 DNS 配置测试子域，建立反向代理和 HTTPS。
5. 编写可重复的构建、迁移、启动及健康检查脚本，先手动验证。
6. 在 GitHub Settings 配置 Secrets/Variables；支持时创建 staging Environment，保存该环境专用变量和凭证。不得提交实际秘密。
7. Actions 检查代码，构建标记提交 SHA 的镜像或产物，经 SSH 或平台 API 部署。
8. 部署后执行健康检查，记录 URL、SHA 与日志；失败停止，不标为成功。
9. 将所需检查加入 main 的保护规则。用测试 PR 验证合并后部署，再更新本文的真实运行方法。

GitHub Environment 只管理配置、保护规则和部署记录，不提供服务器。私有仓库的 Environments、保护规则、审批等受套餐限制；若不可用，改用仓库 Secrets 和受控发布流程，不假装审批已生效。

## 合并前的分支预览

推送功能分支不等于合并或创建 PR。配置好预览后，成员可以在正式提 PR 前在线自测。

### 成员使用步骤

1. 本地 commit 后执行 `git push -u origin <自己的分支名>`。
2. 打开 GitHub Actions，选择预览工作流，点击 Run workflow。
3. 选择自己的分支及需要的预览标识，运行工作流。
4. 等待检查、构建和部署通过，从运行摘要获取 URL、SHA 或测试包。
5. 自测并记录结果；继续 push 后再次部署，准备好再创建 PR。

使用 workflow_dispatch 时，工作流必须先存在默认分支才能正常启用该入口。当前尚无此工作流，需维护者先完成部署配置；不能在尚未初始化工作流的分支里凭空使用。

### 维护者实现要求

- 为每个分支或 PR 建立稳定环境标识；不能直接把带 `/` 的分支名拼成域名、目录或 shell 命令，需校验和规范化。
- 同一环境部署串行执行，避免旧运行最后完成覆盖新版本；部署策略同时防止中断迁移。
- 纯前端改动可连接兼容的 staging 后端；接口变更时部署配套后端和隔离数据库。
- 资源有限可用独立的单个 preview 槽位，记录当前占用者和 SHA，同一时刻仅测试一组改动。
- 分支删除、PR 关闭后清理环境，数据库清理仅作用于预览资源。
- 不将来自外部 fork 或其他不可信代码自动部署到持有正式凭证的环境，不以 pull_request_target 执行未可信代码。
- 网页预览覆盖页面和业务流程；原生 APP 仍需构建及真机分发。

后续可将预览触发改为限定的功能分支 push，但频繁构建有资源、分钟数和平台成本，先按需运行更便于控制。

## 发布与正式部署

1. MVP 在 staging 验收，记录具体 SHA、迁移和已知问题。
2. 为该提交创建版本 Tag。构建固定版本产物，标识 SHA/版本，不用浮动 latest 代替实际版本记录。
3. 建立 Release 草稿，附 APK、发布说明、部署指南和对应镜像信息。
4. 选择固定版本部署 production，使用独立凭证；可用时配置环境审批，否则用受控手动运行和团队批准流程。
5. 先确认备份和数据库迁移策略，再部署与健康检查；迁移并不一定可逆。
6. 验证后公开 Release，记录正式环境版本。APP 商店发布另有签名、审核和分发流程。

同一服务器产物尽量在验证后晋升，避免重新构建出不同依赖；客户端 API 地址可能在构建时固化，测试包与正式包通常需要不同配置，分别验证。

失败时保留日志和版本记录，恢复上一固定产物；数据库若不兼容，不可盲目回滚代码。部署任务中明确备份恢复、兼容性及失败责任人。创建 Release 不自动部署，只有工作流明确连接这些步骤时才会发生。

## Capacitor 构建与首阶段验证包

以下为后续任务的构建设计，当前没有可执行打包入口或已生成 APK。完整流程为：Vite 构建前端静态资源 → Capacitor 同步到原生工程 → Android/iOS 原生构建及签名 → 按渠道分发与真机验证。网页构建本身不会生成 APP 安装包。

- 前端资源随安装包放入手机，通过 WebView 展示；原生能力由 platform/ 中的适配层调用插件。后端独立运行，不随 APK 打包，也不在手机上启动 FastAPI 或数据库。
- 首阶段在 frontend/android/ 创建原生工程，使用 Android Studio 或对应构建工具生成测试 APK。frontend/ios/ 在后续 iOS 任务中创建，使用 Mac/Xcode 及相应签名配置；当前不要求 iOS 包。
- 后续任务需明确应用标识、图标、Capacitor 与原生工具链版本、Web 产物目录、测试签名和安装步骤，提交必要原生工程配置；不提交私密签名材料、构建缓存或安装包产物。
- 原型的相对资源 base、哈希路由、地图与字体资源在迁移后继续验证；资源须从安装包正常加载，保留字体、Three.js 和地图许可证，公众分发显示 OSM 署名。
- Android API 地址使用手机可访问的开发后端。网页开发代理不会自动随 APP 包运行；本地联调需核对监听地址、网络、防火墙及原生请求来源。开发环境若需允许 HTTP，只使用明确限定的测试配置，后续正式 API 使用 HTTPS。
- 前端资源或原生配置变更后重新构建、同步并生成验证包；更新后端不会自动更新手机上的前端代码。测试包标明版本与提交，按 [测试说明](testing.md#首阶段-demo-验收) 验证，记录包来源与安装方式。

最小 Android 验证需单独安排任务，补充 #20/#23 网页任务之外的验收和分发材料；自动打包与部署继续由后续基础设施任务推进。本次不创建远程任务或修改其状态。

参考：[Capacitor 构建流程](https://capacitorjs.com/docs/basics/workflow)、[Android](https://capacitorjs.com/docs/android)、[iOS](https://capacitorjs.com/docs/ios)。

## APP 测试与分发补充

Android 可生成签名测试 APK，让成员安装并连接测试后端。iOS 免费 Apple Account 可做有限个人真机开发测试，付费 Developer Program 支持 TestFlight 等渠道，官方年费为 99 美元或当地货币价格，应在注册时核对。TestFlight 构建最长测试 90 天，外部测试可能需要 Beta 审核，不能作为永久发布渠道。需要本地 iOS 原生调试时准备 Mac/Xcode。

正式上架准备功能完整性、审核访问账号、隐私说明、账号删除和第三方数据处理说明；中国大陆分发所需备案材料按应用功能和苹果要求核实。目标是阶段性交付时，测试渠道与商店正式上架分开安排。服务端更新不会自动替换安装在手机里的原生代码。
